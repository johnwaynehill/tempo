- **Daily AI spend cap**, the last item on the API-hardening roadmap after rate limiting (#80) and key scoping (#85). Rate limiting bounds requests, not money: the proxy forwarded whatever body a caller sent, so a leaked `ai`-scoped key could set a 64k `max_tokens` and run roughly $30 a minute at the 30/min limit. Now every call through `POST /api/anthropic/v1/messages` is priced from the response's `usage` block (input, output, cache read/write, per-model rates in `api/src/lib/ai-pricing.ts`) and added to a new `ai_usage_daily` row for the user's local day (`autoplan_timezone`; migration `Docs/migrations/2026-09-13-ai-usage-daily.sql`, applied to prod by hand). Once the day's total reaches `AI_DAILY_CAP_USD` (default **$2**, about five times a heavy real day; `0` disables) the proxy returns `429` with an Anthropic-shaped `{ error: { type: "ai_budget_exceeded", cap_usd, spent_usd, resets_at } }`. One cap covers browser and API-key traffic alike. Two cheaper guards ride along in the same `aiBudget` middleware: the model must be one Tempo uses (400 otherwise, so a leaked key can't be pointed at a pricier model) and `max_tokens` is clamped to 4096. Streams are tee'd so the final `message_delta` usage is charged when they end; a stream that dies before `message_start` is charged an input-only estimate. The morning autoplan cron counts toward the same cap and falls back to the heuristic picker when over it. Client: Tempo AI chat shows "Tempo AI is resting until tomorrow" on that error instead of a raw message; the one-line helpers (pick for me, smart capture, completion toast) already fail quietly. Settings gains a **Tempo AI** section with today's spend against the cap, a sage progress bar, and the 7-day total, fed by new `GET /api/ai-usage`. Verified: script against `ai-pricing.ts` (cost math incl. cache multipliers, env parsing, model allowlist, SSE usage extraction from a real-shaped stream incl. abort before `message_start`, local-date and next-midnight across timezones); against the local API with the dev user: disallowed model → 400, a real 5-token call → row with 1 request and the right cost, a streaming call → output tokens recorded, a planted $2 row → 429 with the documented body, `GET /api/ai-usage` and the Settings section reflect it. `tsc` clean on `api` and frontend. **Also set a monthly spend limit on the Anthropic Console workspace as the backstop outside this code.**

## 2026-07-01
- Fix autoplan suggesting Chore-project todos on the wrong day, and crowding out real priorities. Chores (recurring cleaning tasks) were scored the same as everything else, so they'd start earning strong due-date-urgency points up to a week before their due date and — worse — kept scoring at the **maximum** urgency forever once overdue, since `daysUntil < 0` also returns `1.0`. With ~10 rotating Chore todos, that meant they routinely crowded the 12-candidate pool fed to the AI/heuristic picker, pushing out genuinely high-priority work and making the Today list easy to ignore. Chore-project todos (`Chore`, matched case-insensitively) are now a hard candidacy gate in both the server autoplan (`api/src/lib/autoplan.ts`) and the client fallback (`src/lib/scoring.ts`): eligible **only** on their literal due date, excluded entirely otherwise — not just deprioritized. Also fixes a latent bug in the server-side date math: due-date-urgency comparisons used the API server's local timezone (UTC on Railway) instead of the user's configured `autoplanTimezone`, which could misjudge which calendar day a due date "counts as" near timezone boundaries; day comparisons are now anchored to the user's IANA timezone throughout. Verified against production data (20/20 assertions, incl. every real Chore todo's actual due date) and a clean `tsc` build on both `api` and the frontend; no schema or env changes, no UI change. `DUE_DATE_ONLY_PROJECTS` is a small constant in each file — easy to extend if another project needs the same "exact day only" rule.
